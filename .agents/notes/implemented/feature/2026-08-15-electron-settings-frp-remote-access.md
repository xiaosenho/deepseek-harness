# Agent Note: Electron Settings and FRP remote access

Status: implemented

English | [中文](2026-08-15-electron-settings-frp-remote-access.zh.md)

## Problem

The Electron desktop host can expose its owned WebUI to a trusted LAN, but a device outside that network cannot reach it through an operator-owned `frps` server. The LAN workflow also keeps every control in native menus and dialogs, which cannot present the server, port, executable, token, public-origin, and transport-risk fields needed for a configurable reverse tunnel.

Adding FRP is not only a connection setting. Electron must keep the WebUI on loopback, admit the public Host authority only with a fresh Harness bearer, require a different main-owned bearer from loopback Hosts that may arrive through the tunnel, distinguish both per-enable values from the persistent `frps` authentication token, prove the selected TCP proxy is published before disclosing its URL, and stop both owned process trees before revoking the mode. A public TCP proxy also makes the existing plaintext warning more consequential because Internet traffic can traverse the browser-facing part of the route.

## Decision

This decision partially supersedes exactly two parts of the [Electron LAN access decision](2026-08-14-electron-lan-access.md): remote-access controls are no longer native-only for the managed loopback renderer, and Electron remote access is no longer limited to a directly reachable LAN. That note remains the authority for fresh Harness bearer generation, fragment-to-cookie delivery, token-granted Host access, replacement-process rollback, shutdown ordering, and clipboard residue. This note extends those rules to the Settings renderer and FRP process.

It also supersedes the [Electron Web host decision](../architecture/2026-08-14-electron-web-profile-host.md) only where that decision excludes every preload and rejects a narrow remote-access bridge: Electron now installs the limited desktop bridge in its owned loopback renderer. The host decision remains the authority for application composition, process ownership, navigation, sandboxing, packaging, and external-URL mode. It supersedes the [PocketBase OTA decision](2026-08-14-electron-pocketbase-ota-updates.md) only where that decision makes update presentation native-only, excludes update state and methods from a preload, and rejects WebUI update controls: the managed renderer now presents redacted update state and delegates checks and installation to main. The OTA decision remains the authority for release selection, artifact trust, download, installation, and shutdown ordering.

### Managed renderer controls

`@deepseek-ai/dsh-client-ui-desktop-electron` contributes Remote Access Settings, General Settings software information, and the sidebar update badge only when the complete `window.dshElectron` preload API exists. Electron installs that preload only for its owned WebUI window. Generic browsers, remote LAN and FRP pages, and `DSH_ELECTRON_URL` mode receive neither the bridge nor the contributions. Native menu commands remain an alternate local control path.

Electron main authorizes every bridge invocation against the current `BrowserWindow`, its main frame, and the current application origin. The renderer receives redacted desktop state: the public endpoint has no token fragment, and the optional `frps` token is represented only by `authTokenConfigured`. Token edits cross IPC as explicit keep, replace, or clear operations. Copying a connection URL invokes a main-process clipboard write and returns only success or failure, so the public Harness bearer never returns to renderer state. FRP uses a second, distinct local bearer because its transparent TCP proxy makes public clients appear as loopback peers to the WebUI. Main installs that value as an `HttpOnly` `/api` cookie before loading the local renderer; it does not cross the preload bridge or enter renderer-readable JavaScript state.

Remote-access preferences persist in a versioned owner-only JSON file under Electron user data, but enabled state and the per-enable public and local Harness bearers do not. Electron encrypts the optional `frps` token with `safeStorage` and fails the save or load when the operating-system secret store cannot protect it. Settings changes are accepted only while the controller is settled in loopback mode, preventing a displayed active endpoint from diverging from its process configuration.

### FRP publication

FRP mode is enabled on macOS and Linux. It keeps the Electron-owned WebUI on `127.0.0.1` and adds its validated public authority to `trustedHosts`. Windows retains the configuration but rejects FRP enablement before stopping the active loopback backend because its WebUI and `frpc` trees do not yet have durable Job Object ownership. The form stores a bare `serverAddress`, `serverPort`, fixed or automatic `remotePort`, optional `publicOrigin`, `frpc` executable, required TLS trusted-CA file, optional certificate server name, optional `frps` token, and explicit plaintext acknowledgement. Defaults are control port `7000`, automatic remote port `0`, no token, no separate origin, and executable `frpc`; the operator must still provide the public IP or hostname and the CA that issued the `frps` certificate. A blank certificate server name verifies against `serverAddress`, while an explicit value supports a certificate whose DNS identity differs from the connection address. A separate public origin requires a fixed remote port.

Electron uses a system-provided `frpc`; it neither bundles nor downloads the binary. `DSH_ELECTRON_FRPC_PATH` supplies the first-run default when no preferences file exists, the default otherwise resolves `frpc` through `PATH`, and a saved executable field takes precedence on later launches. The selected binary must support the generated JSON fields and authenticated `/api/status` response; Electron does not pin or negotiate an `frpc` version. The child receives a scrubbed parent environment that excludes `DSH_*` and credential-shaped variables while retaining ordinary process-launch settings.

Each enable creates a mode-specific WebUI with a new public Harness bearer; FRP also creates a different local bearer and configures the Connection plugin to require it from every loopback Host. The main process passes both through separate child-only environment fields, retains both outside renderer state, and installs only the local bearer into the managed loopback cookie store. It then writes an owner-only temporary `frpc.json`. The JSON contains `serverAddr`, `serverPort`, `loginFailExit: true`, optional token authentication, a TLS control transport with `trustedCaFile` and a resolved `serverName`, one encrypted TCP proxy from `127.0.0.1:LOCAL_PORT` to the configured `remotePort`, console logging, and a loopback status server with random credentials. Secrets therefore stay out of argv but remain in the short-lived private file. Electron starts `frpc -c CONFIG`, polls the authenticated status API, and declares readiness only when the exact random proxy name reports `status: "running"` with a parseable public port. A login-success log, process liveness, or the status server alone is insufficient, and the returned address supplies an automatically assigned port.

Authentication, publication, port-conflict, disallowed-port, malformed-status, process-exit, and 20-second readiness failures all fail the transition. Electron stops `frpc` before the WebUI and removes the temporary directory, then applies the existing replacement rollback. On supported FRP platforms, an unexpected leader exit after readiness still joins the complete process tree, removes the private directory, and restores loopback mode; cleanup failure retains ownership for a later stop retry, and failure to restore enters the existing fatal shutdown path. A normal disable succeeds only after both owned trees stop; unresolved cleanup follows the fatal path rather than a successful disabled transition. Windows `taskkill` cleanup accepts only a zero exit status and never treats leader exit state as tree quiescence.

### Public transport security

Every LAN or FRP enable creates a fresh public Harness bearer and publishes it only in the complete `#dsh-access=TOKEN` URL. The stored `frps` token authenticates `frpc` to the operator's server and does not authorize browser API calls; the public Harness bearer authorizes those calls and is invalidated by stopping its WebUI process. FRP's separate local bearer authenticates the Electron-managed loopback renderer and is removed before navigation away from FRP. A tunnel caller that sends a loopback Host must present this unknown local bearer; the public bearer cannot substitute for it, so explicitly loopback-only methods remain local. The public Host authority alone grants no privilege.

The generated `frpc` configuration authenticates the `frps` control endpoint with the required CA and resolved certificate server name, and enables encryption for proxy transport. This does not create browser-facing HTTPS or authenticate the public endpoint to a browser. With no `publicOrigin`, Electron derives a plaintext `http://SERVER:ACTUAL_PORT` endpoint. A configured `publicOrigin` changes the displayed URL and trusted Host authority only; an `https://` value is valid solely when an external TLS terminator for that authority actually forwards to the fixed FRP port. Plaintext public access requires an explicit acknowledgement because anyone who intercepts the bearer can control the Harness Host. On an actual HTTPS origin, fragment consumption writes the API bearer cookie with `Secure` so an HTTP downgrade cannot receive it.

## Verification

Electron coverage pins owner-only backend binding, distinct public and local bearer retention in main, local `HttpOnly` cookie replacement, validated configuration and redaction, IPC caller authorization, authenticated `frpc` TLS fields, scrubbed child environment, authenticated status readiness including automatic ports and proxy errors, process-tree joining, cleanup retry, stop ordering, rollback, unexpected-exit recovery, Windows rejection before restart, and checked Windows `taskkill` results. Connection coverage pins that an FRP-shaped loopback peer cannot use a forged loopback Host with no cookie or with the public bearer, while the separate local bearer admits the managed renderer across HTTP, WebSocket, shared interceptors, and dedicated RPC channels. Client-package coverage pins strict state parsing, serialized bridge commands, transition polling, conditional registration, FRP form validation, redacted endpoint rendering, main-owned copy, update state, and the absence of contributions without the preload. Browser coverage pins `Secure` public bearer cookies for HTTPS origins. The assembled Web overlay keeps FRP on loopback while admitting only its configured public authority and distinct current bearers. A keyless Web scenario loads the real Host, client catalog, and built plugin bundle, then snapshots configured and enabled FRP Settings states through a preload-only fixture and proves no secret reaches visible text.

## Alternatives considered

**Keep all controls in native menus and dialogs.** Rejected because a multi-field FRP configuration and its validation need a stable Settings surface. The preload stays limited to the owned loopback renderer and exposes commands rather than native process or clipboard primitives.

**Bundle a pinned `frpc` in every installer.** Rejected for this implementation because it adds a platform-specific binary release, provenance, version, and legal-maintenance obligation. Using a system binary or explicit path keeps that responsibility with the operator, at the cost of requiring installation and compatibility management outside the application.

**Enable Windows FRP with PID-based `taskkill` ownership.** Rejected because a leader can exit before cleanup while descendants continue under different process ancestry. Windows FRP requires a Job Object established before either WebUI or `frpc` descendants can start, retained independently of the leader PID, and queried until its active-process count reaches zero.

**Accept only a public server IP and hard-code every other FRP value.** Rejected because real `frps` deployments vary the control port, authentication token, certificate identity, trusted CA, allowed public ports, and HTTPS termination authority. Requiring a CA prevents the configurable system binary from accepting an unauthenticated TLS control server.

**Parse `frpc` logs for readiness.** Rejected because control login can succeed while the proxy is retrying or rejected, log text is not a status protocol, and automatic port allocation requires the reported public address. The authenticated loopback API provides the proxy-specific running state and port.

**Return any secret to the renderer.** Rejected because Settings needs only redacted configuration and an atomic main-owned copy action. Giving a dynamically composed browser plugin the `frps` token or public Harness bearer would widen credential exposure without enabling another required operation. The managed window needs the local bearer only as a transport credential, so Electron stores it in an `HttpOnly` cookie instead of JavaScript state.

**Treat an `https://` public origin as TLS configuration.** Rejected because a URL string cannot install a certificate or terminate TLS. It is an assertion about an external deployment component, so plaintext requires acknowledgement and HTTPS remains the operator's verifiable responsibility.

## Consequences

On macOS or Linux, an operator can publish the Electron-owned Harness through an existing `frps` server by configuring its public address and the CA that issued its certificate. The certificate must cover the address or the explicit certificate server name. Other deployments must also configure matching control authentication, an allowed and firewalled public port, and any external HTTPS authority. The application cannot determine whether a system `frpc` version is compatible before starting it, so incompatibility appears as a failed enable followed by rollback. Windows can save the same preferences but cannot enable FRP.

The renderer gains desktop-specific controls but not any secret or general Electron capabilities. Its two FRP path controls invoke a purpose-discriminated main-process file selector; the bridge returns only one selected absolute path or cancellation and exposes no general filesystem operation. Saving preferences can persist an encrypted `frps` token, while each enable rotates the public Harness bearer, FRP additionally rotates the local bearer, and each disable or restart revokes them. Enabling, disabling, and recovery replace the WebUI origin and can interrupt active work.

Electron applies its native-and-browse directory-picker overlay on every desktop platform. The managed loopback renderer selects a workspace through the native helper, while authenticated LAN and FRP renderers select the same Host filesystem path through the provider's in-app browser. The remote flow therefore does not call the loopback-only `host.pickDirectory` RPC.

Raw FRP TCP publication remains plaintext from browser to public endpoint even though the internal FRP hop enables encryption. Internet use without real browser-validated HTTPS can expose the Host-control bearer and all application traffic; the acknowledgement makes that choice explicit but provides no protection. These desktop controls and tunnel states remain outside the Session log and add no model-visible input.
