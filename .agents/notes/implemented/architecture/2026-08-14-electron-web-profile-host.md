# Agent Note: Electron wraps the existing WebUI

Status: implemented

English | [中文](2026-08-14-electron-web-profile-host.zh.md)

## Problem

DeepSeek Harness has a browser application and a `dsh web` composition but no native desktop window. A desktop wrapper must reuse that application without creating a second client composition, transport, storage implementation, or privileged renderer runtime.

## Decision

`apps/electron` is a product host over the published `@deepseek-ai/dsh` dependency closure. Its main process starts the packaged CLI with `web` in a hidden detached process tree, waits for the existing readiness line, and loads that process's loopback HTTP origin in `BrowserWindow`. Every application launch starts with a loopback-only backend. Native application-menu commands can make main replace that process with an authenticated Electron-overlay backend bound to `0.0.0.0`, or replace it again with a loopback-only backend; each replacement uses port `0`, and main loads its new loopback origin after readiness. Main owns the confirmation and connection-details dialogs plus clipboard writes. The complete access URL never enters the renderer, native window title, or a menu label. [Electron LAN access uses an ephemeral bearer URL](../feature/2026-08-14-electron-lan-access.md) owns the enablement, credential, and security decision. Source runs use the repository root as the command working directory; packaged runs default to the user's home. `DSH_ELECTRON_CWD` selects another directory. `DSH_ELECTRON_URL` deliberately bypasses process startup for an already-running HTTP or HTTPS WebUI and omits the **Remote Access** menu because Electron does not own that backend.

The process is an ordinary operating-system child rather than an Electron utility process. It uses the packaged Electron executable with `ELECTRON_RUN_AS_NODE=1` and `--expose-internals`, so the CLI uses the packaged runtime and Electron-rebuilt native dependencies without requiring an external Node installation. Electron shutdown sends `SIGTERM` to the detached process group on POSIX, escalates to `SIGKILL` after a bounded grace period, and waits for group absence; Windows uses `taskkill /T /F` and waits for the child exit edge.

A requested backend that fails readiness may roll back to the previous mode on a new origin; main loads that origin and reports a recoverable mode-change failure. An active process that cannot be stopped safely, a rollback that cannot restore a usable backend, or a ready replacement origin that `BrowserWindow.loadURL()` cannot load leaves no safe desktop-host state. Main presents one fatal native error and requests quit after acknowledgement. The exit barrier runs process-tree shutdown, remains closed after a failed cleanup attempt, and permits a later attempt; Electron exits only after cleanup succeeds. The next application launch creates a new loopback-only backend rather than restoring the interrupted mode.

On Windows, the child also applies an Electron-owned directory-picker overlay. A loopback renderer opens the operating-system chooser through a private child-to-main IPC bridge and a dedicated, abortable Electron helper process; a LAN renderer uses the same host's direct-filesystem browse operations. [Electron owns the Windows native directory picker](2026-08-14-electron-owned-native-directory-picker.md) records this mixed interaction, its lifecycle, and why it replaces the incompatible Koffi/COM path only for packaged Electron. Other platforms retain the adaptive picker.

The Electron-managed renderer receives no Electron preload or renderer IPC bridge. Remote-access menu commands invoke the main-owned controller directly; native dialogs present confirmations and the complete bearer URL, and main writes that value to the operating-system clipboard. Phone browsers and ordinary WebUI deployments therefore receive no Electron-specific remote controls, while `DSH_ELECTRON_URL` mode does not install the menu commands. Node integration and WebView support are disabled; context isolation and Chromium sandboxing are enabled. Main-window navigation is restricted to the exact current WebUI origin, which main replaces when a new backend becomes ready. Other HTTP and HTTPS origins open through the operating system, while non-Web schemes are rejected. The dedicated Chromium user-data directory prevents Electron storage and single-instance locks from colliding with unrelated Electron applications.

The Electron package is not a Cordis plugin and contributes no session event, prompt section, tool, API route, or client slot. Its production dependencies on `@deepseek-ai/dsh` and the CLI host's required `@deepseek-ai/cordis-plugin-group` peer make electron-builder include the CLI, Web frontend, bundles, plugins, and their runtime dependencies in the application. Those files remain an ordinary dependency tree under the application resources rather than an ASAR archive because profile module fallback creates real filesystem links to installed packages. The Web profile continues to own every host and browser plugin, workspace operation, credential read, setting, and durable session write.

## Alternatives considered

**Reimplement the Web transport in Electron.** Rejected because the Web application depends on HTTP routes, WebSocket streams, boot-manifest injection, and dynamic client bundles already provided by `dsh web`.

**Run the CLI inside an Electron utility process.** Rejected because its module-loader behavior and lifecycle are coupled to the main Electron instance. A separate Electron executable in Node mode supplies the same packaged ABI while preserving an independently terminable process tree.

**Expose remote-access operations through a narrow preload bridge.** Rejected because backend lifecycle, credential disclosure, and clipboard access are Electron main responsibilities, while the Web application needs no renderer access to them. Native menu commands and dialogs keep both the operations and bearer value outside the dynamically composed renderer.

**Require the user to start WebUI separately.** Retained as the explicit `DSH_ELECTRON_URL` mode, but not the default because the desktop application should open with one command.

## Consequences

The desktop application presents the same UI and model-visible context as `dsh web`. Its local Windows window receives a native directory chooser, while a phone on the same trusted LAN can use the tokenized URL shown in the native details dialog and the in-app directory browser. Backend replacement interrupts work owned by the previous WebUI process, but the native window loads the replacement origin automatically; a fatal replacement failure requests application exit, and the exit barrier keeps that exit blocked until owned-process cleanup succeeds. Reopening returns to loopback-only mode. Development startup is one command, application shutdown stops the owned WebUI and any active chooser helper, and packaged applications require no external source tree, Node.js, or package manager. Distribution produces a product-icon-branded macOS ARM64 DMG and Windows x64 NSIS installer. Cross-packaging installs the Windows x64 optional native dependency variants and uses their prebuilt binaries instead of attempting node-gyp cross-compilation. Apple Silicon builders require Rosetta 2 for electron-builder's x86_64 NSIS compiler; release jobs still need signing and macOS notarization.
